## 1. The RAK3172 was never dead — a stale binary was the whole fault

Node 1 was running `gateway/wifi_check`, which never touches UART2, so the
"24 probes over 40 s, no reply" recorded on 6 Nov was nobody probing the module. The
boot banner names the firmware: opening the port **DTR low** resets the C3 and prints
it. Reflashing `-DROLE=2 -DNODE_ID=1` → the module answered on the **first** probe,
acked every send, and its RA-02 decoded all three collars.

Acceptance against base3 (`python3 tools/poc_watch.py 120`): 15 reports, `missed 0`,
915 rssi −21..−16 dBm, all three collars at the house, base-vs-node RSSI inside ±3 dB
(mean +1.2, spread −3..+3). Node 1 is live in Home Assistant:
`sensor.cat_base_3_node_1_node_3_packets` climbs every 8 s, `in_range` is `on`.

Three observer bugs made a healthy link look dead, and all three are fixed in
`tools/poc_watch.py`: base3 prints `[RX] node …` only when verbose is on (key `v` —
the watch now sends `v`), the regex was pinned to the old `cat 2 rssi -90` wording, and
the firmware prints `cat <id> seq <collarseq> r<rssi>` with base3 omitting `dBm`/`dB`.

## 2. Battery monitoring — firmware done, hardware not

Node reports now carry a tail: `CAT1 12 c1 s163 r-55 b3325 q1` (`b` = millivolts at the
cell, `q` = TP5000 CHRG, 1 = charging). Absence is published as JSON null, so a node
with no divider fitted does not read as a flat cell. Volts, never a percentage:
LiFePO4's curve is flat.

Done and verified on the bench:

- `poc915` node role: `BAT_ADC`/`BAT_DIV`/`CHRG_PIN` build flags, `battMv()`/`chgState()`
  (under 2000 mV is read as "no cell"), key `u` prints `[batt] mV charge ADC divider`,
  the beat line carries `batt`/`chg`, tail appended to the report.
- `poc915/rak_event.h` `tailInt()` parses `b`/`q`; tests added to
  `poc915/test_rak_event.cpp` — **all pass**.
- `gateway/state_json.h` publishes `nb`/`nq` per node, discovery records for
  `base3_n<N>_battery` (unit `V`, device_class `voltage`) and `base3_n<N>_charging`.
  `gateway/test_state_json.cpp` — **all pass**.
- base3 console prints `cell <mV> chg <n>` on the `[RX]` line and in the `[v]` report.
- HA: node battery + charging entities exist for n0..n3, and node 1's two tiles were
  added to `dashboard-cats` (`python3 tools/cats_dashboard.py --base base3 --node 1 2 3
  --add-tiles --write`).
- `tools/node_check.py` (new) prints per-node `in_range / last_seen / packets / missed /
  cell V / charging`, warns below 3.10 V, exits nonzero if no node is reporting.
  `python3 tools/node_check.py`, `--watch 120`, `--nodes 1,2`. It reads entity ids out of
  the registry by unique_id and states over REST, because this install answers **no**
  state WebSocket command (`get_state`, `state/get`, `state/get_all` →
  `unknown_command`). `HA_TOKEN` in `~/.zshrc` is valid; the one in `AGENTS.md` is not.

Two silent traps found and fixed:

## 3. Design written, not built

`docs/plans/remote-nodes/fota-and-field-check.md` — nodes out of 2.4 GHz range make BLE
the transport. Facts from the toolchain: the **default** ESP32 partition scheme already
has `app0` + `app1` (1.3 MB each), the sketch is 340 KB, and core 3.3.12 ships
`ArduinoOTA` + `tools/espota.py`. Plan: BLE service `CATNODE-<id>` with `STATUS`/
`OTA_CTRL`/`OTA_DATA`/`OTA_EVT`, `esp_ota_ops` writing the **other** slot, whole-image
CRC32 before switching boot partition, rollback marked valid only after a base ack, and
BLE opened by a magnet on the enclosure (never advertising permanently). Client is
`tools/ble_ota.py` (bleak, the pattern of `tools/ble_roster.py`) on a laptop, not the
phone app. 915 is for **config commands**, not for code (~1.2 KB/s, 10–20 min, blinds
reporting). ESPHome's OTA is WiFi-only, so it buys nothing for the deep-jungle nodes.

Throughput numbers in that file are arithmetic, not measured. Replace them.
